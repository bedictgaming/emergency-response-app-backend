# Release and monitoring acceptance

These checks do not authorize deployment, evidence deletion, real incident creation, email or push to real recipients. Keep dashboards supervised. A local mock, configured key, or empty queue is not proof of delivery.

## CI and dependencies

Each application repository now has its own `.github/workflows/ci.yml`. Commit/push and confirm actual Actions results before claiming remote CI is active; configure required branch checks separately. Backend CI uses an unreachable dummy database and disables the opt-in integration suites. Frontend CI uses a local mocked export, not a live deployment mode. No cloud secrets belong in pull-request jobs. Database integration, deployment and migration remain separate gates; take and verify an encrypted backup before any applied migration.

Run `node scripts/check-dependency-audit.mjs` in each repository. It fails on runtime advisories, new advisories or an unavailable audit. The sole known build-only exception is [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), unpatched at review on October 3, 2026. This is containment, not remediation. Its explicit exception expires October 17, 2026. Do not accept untrusted glob patterns. Review upstream before expiry; do not force major dependency downgrades. Backend runtime image uses production-only dependencies, copies compiled Prisma and mail templates, and runs as `node`; CI must build that image on Linux before release.

## Health and queues

Monitor anonymous `/healthz` and `/readyz` at a modest interval (e.g. one minute), with a client deadline of five seconds. Alert on three consecutive failures or repeated bursts; record timestamp, endpoint, HTTP status, latency and sanitized request ID. Separate a transport/TLS failure from a 503 database dependency failure. Do not restart/redeploy blindly or repeatedly probe at high frequency. Correlate with Railway deployment/instance events, database-pool logs and database-provider status; this code does not establish the cause of historical network failures.

`/readyz` tests only database reachability. New code returns within three seconds, shares one in-flight check and briefly caches results; a timeout does not cancel its underlying query. Connection acquisition is bounded at ten seconds. It does not certify account-email delivery, Cloudinary, push, replicas or capacity.

An authorized operator can run `npx tsx scripts/inspect-operations.ts --read-only` against the deliberately selected environment. This reads only notification-outbox aggregates and the oldest unfinished timestamp. It never drains/retries jobs, deletes assets or exposes recipients/payloads/IDs/last-error strings. Exit 1 means exhausted retries, oldest unfinished age over fifteen minutes, or inspection failure. Configure your operator scheduler/monitor separately; merely adding this script does not schedule it. Investigate failures against the dashboard response process; do not requeue potentially delivered work blindly. Check missing keys/disabled worker independently.

## Daily backup acceptance

Verify the actual daily schedule, last success, key custody and off-site copy. On the latest authorized encrypted file, run:

```
npx tsx scripts/verify-encrypted-backup.ts <exact-backup.json.enc> --max-age-hours 26
```

This validates AES-GCM authentication, JSON/table structure and backup age without printing private rows. Without the age flag it validates an historical file but does not demonstrate daily freshness. A metadata timestamp alone is insufficient. Confirm a restore into an explicitly disposable database and reconcile table/report counts; do not restore into production. Keep keys and decrypted contents out of Git, logs and support tickets. No automated daily job or off-site backup is created by this change.

`MAIL_PROVIDER=brevo` sends one immediate message through the fixed `https://api.brevo.com/v3/smtp/email` HTTPS API. Despite `smtp` in that HTTP path, this is not an SMTP connection. No new Vercel project/function, relay key or database is required. Production validates `MAIL_FROM` (the bare verified Brevo sender), server-only `BREVO_API_KEY` (an API key, not an SMTP key), and safe `APP_NAME`; SMTP/Resend/relay credentials are not used in this mode. Store the key only in the approved backend secret manager; never commit it, place it in browser settings or paste it in chat. Do not change the live provider merely by following these local setup notes.

The operator's screenshot confirms sender ownership verification, not transactional-platform activation or delivery. Check Brevo account approval/transactional activation before separately authorized controlled sends. Brevo's free plan currently allows 300 sends/day shared across verification and reset requests; excess transactional mail may be queued by Brevo, so a delayed link may expire. This integration adds no retry queue or global daily quota certification. Existing persisted verification cooldown and shared account-message limits remain. Brevo processes recipient addresses and rendered account-email content/capability links as the delivery provider; no citizen import, marketing list, incident/evidence or account database is sent.

Free-email senders may be temporarily rewritten to a Brevo compliant address. Verification of a Gmail mailbox is not DKIM/DMARC authentication of a domain you control. Treat this as a temporary provider accommodation, not assured inbox delivery or a permanent production-domain solution. See [sender requirements](https://help.brevo.com/hc/en-us/articles/14925263522578-Comply-with-Gmail-Yahoo-and-Microsoft-s-requirements-for-email-senders), [free-plan limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan), and [API contract](https://developers.brevo.com/reference/send-transac-email).

Requests refuse redirects, arbitrary destinations, retries and cross-provider fallback; the ten-second deadline includes response reading and receipts cap at 16 KiB. Only HTTP 201 with a bounded nonempty printable `messageId` counts as transport acceptance. Provider errors/receipts/keys/recipients/capability links are not logged. Generic signup/resend/reset responses and `/readyz` never establish inbox receipt. A failed or ambiguous request may already have been accepted: do not replay it automatically.

The shared mailer serves signup verification, verification resend and password reset. `MAIL_PROVIDER=smtp` is the backward-compatible default; `MAIL_PROVIDER=resend` uses the fixed `https://api.resend.com/emails` HTTPS API, not SMTP. Railway [disables SMTP on Free/Trial/Hobby plans](https://docs.railway.com/networking/outbound-networking). Production requires valid settings for only the selected transport.

For Resend, configure only through the backend hosting secret manager:

- `MAIL_PROVIDER=resend`
- `MAIL_FROM=accounts@<your-verified-sending-domain>` (a bare mailbox, not a display-name string)
- `RESEND_API_KEY=<server-only sending key>` (never `NEXT_PUBLIC_*`, browser storage, chat or Git)
- `APP_NAME=Cordova Emergency Response` (optional code fallback: Emergency Response App)

Do not use those angle-bracket examples literally. SMTP values may remain in the existing secret store during a reviewed transition but are not required or used in Resend mode. Never silently fall back to SMTP or resend after an ambiguous response; an accepted send followed by connection/body failure may already have sent a message. HTTPS connection/body work has a ten-second total deadline and a bounded receipt body. Sanitized categories distinguish configuration, authentication, sender restrictions, provider quota/rejection, network, timeout and receipt failures; neither raw provider errors nor email addresses/links/keys/receipt IDs enter routine logs. A transport-accepted log is not an inbox-delivery receipt.

Resend requires a [verified sending domain](https://resend.com/docs/dashboard/domains/introduction) for arbitrary citizen recipients. The `resend.dev` [test sender is limited to the account owner's inbox](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain); production startup rejects that sender. A free `vercel.app` subdomain or Gmail mailbox is not DNS control of a sending domain. Create/verify a domain and sending-only API key in the operator's provider account before authorized production activation. Confirm DNS ownership and provider status; do not buy a domain/plan, alter DNS, register a provider account or activate test mode without separate approval. Current operator reports no domain: implementation can be verified locally but public activation is pending.
